# Database Engineering Standards

## 1. Technology Stack

- PostgreSQL only.
- SQLAlchemy 2.0 for ORM and database access.
- Alembic for database migrations.
- Use psycopg for synchronous or asyncpg for asynchronous PostgreSQL access, according to project architecture.
- Never introduce another database or ORM without approval.

## 2. Database Design

- Follow relational database design principles.
- Use appropriate primary keys, foreign keys and constraints.
- Define `NOT NULL`, `UNIQUE` and `CHECK` constraints where required.
- Use appropriate PostgreSQL data types.
- Use UUID identifiers where appropriate.
- Store timestamps using timezone-aware types and UTC.
- Avoid unnecessary JSONB fields and database denormalization.
- Maintain consistent table and column naming.

## 3. SQLAlchemy 2.0

- Use `DeclarativeBase`, `Mapped` and `mapped_column`.
- Prefer modern SQLAlchemy 2.0 query patterns such as `select()`.
- Keep models, repositories and services separate.
- Avoid legacy SQLAlchemy APIs.
- Use relationships and loading strategies appropriately.
- Never expose SQLAlchemy models directly as public API contracts.

## 4. Session and Transaction Management

- Create database engines at application scope.
- Use session factories.
- Manage session lifecycle through dependencies or a unit-of-work pattern.
- Always release sessions and connections correctly.
- Use transactions for operations requiring atomicity.
- Commit on success and roll back on failure.
- Never share a Session or AsyncSession across concurrent operations.
- Avoid long-running transactions.

## 5. Query Performance

- Use parameterized queries.
- Retrieve only required columns.
- Avoid N+1 queries.
- Use pagination for large collections.
- Apply eager loading when appropriate.
- Create indexes based on actual query patterns.
- Avoid unnecessary joins and database round trips.
- Use `EXPLAIN ANALYZE` to investigate slow queries.
- Avoid premature optimization.

## 6. Alembic Migrations

- Use Alembic for all schema changes.
- Review autogenerated migrations before applying them.
- Keep migrations focused and reversible where practical.
- Never silently delete or rewrite migration history.
- Consider data loss, locking and backward compatibility.
- Do not manually modify production schemas outside the approved migration process.
- Ensure model and migration consistency.

## 7. Database Security

- Never hardcode database credentials.
- Use environment configuration or a secrets manager.
- Apply least-privilege database permissions.
- Use parameterized queries to prevent SQL injection.
- Protect sensitive data.
- Never expose raw SQL errors to API clients.
- Use TLS for database connections where required.
- Never log credentials or sensitive information.

## 8. Async and Sync Consistency

- Choose synchronous or asynchronous database access based on project architecture.
- Use `Session` for synchronous operations.
- Use `AsyncSession` for asynchronous operations.
- Do not mix sync and async database access unnecessarily.
- Never execute blocking database operations directly inside async endpoints.
- Use `await` for asynchronous database operations.

## 9. Implementation Workflow

Before database changes:

1. Inspect existing models and migrations.
2. Understand relationships and dependencies.
3. Identify schema and data integrity requirements.
4. Propose the required changes.
5. Consider migration and deployment risks.

During implementation:

- Update models and repositories.
- Create appropriate Alembic migrations.
- Preserve existing data and API compatibility.
- Avoid unrelated schema changes.

Do not create or execute tests during implementation. Testing is allowed only after implementation is complete and the user explicitly approves it.

## 10. Final Review

Verify:

- Correct PostgreSQL schema and relationships.
- SQLAlchemy 2.0 conventions.
- Proper session and transaction management.
- Efficient and secure queries.
- Appropriate indexes and constraints.
- Reviewed Alembic migrations.
- No exposed credentials or sensitive data.
- No unintended breaking database changes.

Follow approved project specifications and existing architecture. Never silently change database design decisions.
